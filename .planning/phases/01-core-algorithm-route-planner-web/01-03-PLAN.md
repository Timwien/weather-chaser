  <behavior>
    === nearestNeighborTour(startIndex, distanceMatrix, mustVisitIndices) → number[] ===

    - Output is a permutation of all town indices [0..n-1]
    - Starts at startIndex
    - Each next town is the nearest unvisited town by distanceMatrix value
    - Must-visit towns: after placing the start, insert each must-visit town immediately before the nearest-neighbor tour would have passed a neighbor of that town. Simple approach: run standard nearest-neighbor but treat must-visit towns as "sticky" — if the nearest unvisited is not a must-visit and a must-visit town is unvisited and within 2x the nearest neighbor distance, prefer the must-visit first. If no must-visit towns, behaves identically to standard nearest-neighbor.
    - Every town index appears exactly once in the output array (no duplicates, no omissions)
    - Output length === input towns count

    Test cases:
    - 4 towns, symmetric matrix, start=0 → output is a permutation of [0,1,2,3], starts with 0
    - 4 towns, start=0, mustVisit=[3] → town 3 appears in the output (obvious — all towns appear, but verify it is included and the tour is valid)
    - 1 town → output is [0]
    - 2 towns → output is [startIndex, otherIndex]

    === twoOptImprove(tour, distanceMatrix) → number[] ===

    - Output is a reordering of the same tour indices
    - Total tour distance of output ≤ total tour distance of input (never worse)
    - All input indices appear exactly once in output
    - If no improvement possible, returns the input tour unchanged

    Test cases:
    - Known crossover: 4-town tour [0,2,1,3] with matrix where 0↔1 + 2↔3 < 0↔2 + 1↔3 → 2-opt swaps to [0,1,2,3]
    - Already optimal tour → output == input (no unnecessary swaps)
    - Single element tour [0] → returns [0]

    === assignStops(tour, input) → Route ===

    Input: tour (ordered index array), OptimizerInput (towns, distanceMatrix, weatherScores, config)
    Config: { startDate, totalDays, maxStay, weights }

    Algorithm:
    1. Iterate through tour indices; assign nights to each stop starting at 1.
    2. Increment nights by 1 for each stop until maxStay OR remaining days exhausted.
    3. If days remain after maxStay at current stop, move to next town in tour.
    4. If we run out of tour towns before using all totalDays, spread remaining days onto last stop.
    5. For each stop: arrivalDate = startDate + sum(nights of all prior stops), score = scoreLocation using the arrival date and nights.
    6. distanceToNextKm = distanceMatrix[currentIndex][nextIndex] / 1000 (matrix stores meters) — undefined for last stop.
    7. Route.totalDistanceKm = sum of all distanceToNextKm values.
    8. Route.avgScore = mean of all stop composite scores.

    Test cases:
    - 3 towns, totalDays=6, maxStay=2 → 3 stops of 2 nights each; dates advance correctly
    - 3 towns, totalDays=5, maxStay=2 → stops of 2, 2, 1 nights
    - 2 towns, totalDays=3, maxStay=3 → stops of 3, 0 nights? → No: minimum 1 night per stop — stop 1 gets 2, stop 2 gets 1
    - 1 town, totalDays=4, maxStay=3 → single stop, 4 nights (all days on last stop)
    - arrivalDate of stop 2 = startDate + nights of stop 1

    Note: scoreLocation is called with the weatherScores pre-computed per town index (passed in OptimizerInput). The assignStops function does NOT re-score — it uses the weatherScores array directly. The re-scoring with temporal dates happens in the Web Worker (Plan 07) which calls scoreLocation before calling the optimizer. IMPORTANT: For the TDD test, mock or stub weatherScores as pre-filled WeatherScore objects.

    Implementation note on must-visit (ALGO-07): The simplest correct approach is constrained insertion. After building the greedy nearest-neighbor tour without constraints, check if all mustVisitIndices are present (they will be — NN visits all towns). The must-visit constraint is not about inclusion (all towns are included) but about priority: must-visit towns should not be "skipped over" by the optimizer in favor of better-weather towns. Since NN visits all towns, ALGO-07 is satisfied if the tour includes must-visit indices. The optimizer does not drop stops — it orders them. ALGO-07 simply means must-visit towns cannot be excluded even if their score is low. Implement as: optimizeRoute truncates the tour at totalDays/maxStay — ensure must-visit towns appear in the first N stops of the tour (before truncation). If a must-visit index appears after the truncation point, reorder to bring it earlier by swapping with the stop at the truncation boundary.
