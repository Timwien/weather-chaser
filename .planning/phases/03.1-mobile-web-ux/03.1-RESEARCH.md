## Summary

Phase 3.1 replaces the existing two-screen toggle (full-screen panel OR full-screen map, switched by a bottom tab bar) with a map-first layout on mobile: the map is permanently the background, a compact floating search bar sits at the top, and all panels (entry config, itinerary, finder results) surface as a three-snap draggable bottom sheet. Desktop layout is completely unchanged.

The codebase is clean and change-localized. The main mechanical surgery points are: (1) `apps/web/src/routes/index.tsx` — remove `mobileView` state and `MobileTabBar`, add `BottomSheet` and `MobileSearchBar` compositions; (2) the four CSS files with `@media (max-width: 768px)` blocks — strip the old full-screen mobile overrides and add new mobile positioning classes; (3) `MapContainer.tsx` — extend `FitRouteOnSelection` with a `bottomPadding` prop, and wire `map.setPadding` to reflect the sheet's current snapped height. Everything else (EntryPanel, ItineraryPanel, WeatherFinderPanel, existing hooks/stores) is reused as sheet content without structural changes.

**Primary recommendation:** Build the bottom sheet as a custom lightweight component (pointer-events drag + CSS transform/transition + snap-point state). Do NOT add `react-modal-sheet` or `vaul` — vaul is explicitly unmaintained; react-modal-sheet requires adding `motion` (~34 kB min) as a new peer dependency for a feature that is easily custom-built with ~80 lines of pointer-event code and CSS transitions. The project has zero animation library dependency today; keeping that true reduces bundle and avoids future upgrade pain.

### No New Library Needed
The custom bottom sheet needs:
- `onPointerDown` / `onPointerMove` / `onPointerUp` on the handle div (pointer capture API)
- `translateY` CSS transform driven by a `useRef` for current drag delta
- Three snap pixel values computed from viewport height (`vh`)
- `transition: transform 200ms ease-out` when snapping (not during drag)
- One `useState` for current snap index

This is ~80 lines of TypeScript + ~40 lines of CSS. It avoids adding `motion` (~34 kB gzip) or a stale library.

## Architecture Patterns

### Recommended Project Structure (new files only)
```
apps/web/src/
├── hooks/
│   └── useIsMobile.ts           # matchMedia(max-width:768px) + resize listener
├── components/
│   └── mobile/
│       ├── MobileBottomSheet.tsx  # 3-snap draggable sheet
│       ├── MobileBottomSheet.css
│       ├── MobileSearchBar.tsx    # Collapsed pill + expanded inline form
│       └── MobileSearchBar.css
```

### Pattern 1: useIsMobile Hook
**What:** `window.matchMedia('(max-width: 768px)')` with `addEventListener('change', ...)` returning a boolean. Used to conditionally render mobile vs desktop layout in `index.tsx`.
**Why:** Same pattern already used in `themeStore.ts` for `matchMedia`. SSR-safe (check `typeof window`). No library needed.
**When to use:** Gate the entire mobile composition in `routes/index.tsx`.

### Pattern 2: Three-Snap Custom Bottom Sheet
**What:** A `position: fixed` div anchored to the bottom, full viewport width, with `translateY` driven by pointer drag. Three snap heights:
- `peek`: sheet top visible at ~80px from bottom (handle + summary strip only)
- `half`: sheet occupies ~50vh
- `full`: sheet occupies ~100vh (minus safe-area-inset-top)

**Snap mechanics:** On `pointerup`, compute nearest snap point from current drag position; set `snapIndex` state; apply CSS `transition: transform 200ms ease-out`. During drag: set transform directly via ref (no state update = no re-render during drag = 60 fps).
**Handle:** A `div` at the top of the sheet with `touch-action: none`. Pointer capture (`setPointerCapture`) ensures drag continues even when pointer leaves the handle.
**Scrim:** A sibling `div` with `position: fixed; inset: 0` and `background: rgba(0,0,0,0.25)`, only rendered/faded-in when `snapIndex === 2` (full height). `pointer-events: none` at peek/half; `pointer-events: auto` at full to catch backdrop taps to close.

### Pattern 3: MobileSearchBar Collapsed/Expanded
**What:** A `position: fixed; top: var(--space-3); left: var(--space-3); right: var(--space-3)` pill component. Two visual states:
- **Collapsed:** 48px-tall pill showing "{location} · {dates} · {criterion icon}" — all derived from `tripConfig` and `searchAreas` in the Zustand store. No separate state needed for the content, only for `isExpanded`.
- **Expanded:** Drops down to auto-height; renders `<DateRangePicker />`, `<LocationInput />`, `<CriteriaSelector />` directly (reuse existing components unchanged). A mode selector (route/finder) sits above them. Close button collapses.

**Hide behavior:** `transform: translateY(-120%)` + `opacity: 0` when `snapIndex === 2` (sheet at full). Triggered by watching sheet's snap index.
**Z-index:** Must be above sheet (sheet at z-index 40; search bar at z-index 50).

### Pattern 4: Panel Reuse as Sheet Content
**What:** `EntryPanel`, `ItineraryPanel`, `WeatherFinderPanel` become children of `MobileBottomSheet` on mobile. Their CSS `position: fixed` declarations do NOT apply inside the sheet because the sheet is the new stacking context.
**How:** On mobile (`useIsMobile()`), `index.tsx` renders:
```
<MapContainer ... />          // always in background
<MobileSearchBar ... />       // floats top, z-index 50
<MobileBottomSheet snapIndex={...} onSnapChange={...}>
  {showEntryPanel && <EntryPanel />}
  {showResults    && <ItineraryPanel ... />}
  {showFinderPanel && <WeatherFinderPanel ... />}
</MobileBottomSheet>
<LoadingOverlay />            // z-index 200, unchanged
```
On desktop, `index.tsx` renders the existing `screen-panel` + `screen-map` layout unchanged.
**Key:** The panels' `position: fixed` CSS rules are **desktop-only** now (the mobile `@media` overrides that made them full-screen are deleted). Inside the sheet, panels use `position: static` (no positioning at all) — the sheet's own `overflow-y: auto` handles scroll. Each panel's `.entry-panel`, `.itinerary-panel`, `.weather-finder-panel` CSS classes need a `@media (max-width: 768px)` rule that resets `position` to `static` and `width/height` to `100%` / `auto`.

### Anti-Patterns to Avoid
- **Re-rendering during drag:** Never update React state on `pointerMove`. Use a ref to drive `element.style.transform` directly. Only update state on `pointerUp` when the snap is determined.
- **Using `display: none` on the map:** The existing code correctly uses `visibility: hidden` to avoid unmounting MapLibre. Keep the map always mounted; the bottom sheet overlays it.
- **Setting `overflow: hidden` on `body` when sheet is open:** This breaks MapLibre touch panning. Use `pointer-events: none` on the map at full-sheet height instead (handled by the scrim).
- **Nesting a scrollable sheet inside a scrollable page:** The sheet content area must be `overflow-y: auto` with `overscroll-behavior: contain` to prevent scroll events from leaking to the map.
- **Accumulating MapLibre padding:** MapLibre has a known bug where padding from `flyTo` accumulates with `fitBounds` padding. Always call `map.getMap().setPadding({ top: 0, right: 0, bottom: 0, left: 0 })` before calling `fitBounds`, then pass the desired `{ padding: { bottom: sheetHeight } }` in the `fitBounds` call.

## Common Pitfalls

### Pitfall 1: MapLibre "padding accumulation" bug
**What goes wrong:** After calling `flyTo({ padding: {...} })` and then `fitBounds({ padding: {...} })`, the final padding is the sum of both — markers end up with double offset, partially off-screen.
**Why it happens:** MapLibre GL JS maintains a persistent internal padding state. Each animated camera operation adds to it unless explicitly reset.
**How to avoid:** Before any `fitBounds` call, call `map.getMap().setPadding({ top: 0, right: 0, bottom: 0, left: 0 })`. Then pass the desired padding in `fitBounds`'s `padding` option. See: [maplibre issue #4095](https://github.com/maplibre/maplibre-gl-js/issues/4095) and [discussion #2984](https://github.com/maplibre/maplibre-gl-js/discussions/2984).
**Warning signs:** Markers appear consistently offset even after map movement.

### Pitfall 2: Touch scroll vs drag-to-snap conflict
**What goes wrong:** When the sheet content is scrollable (long itinerary list), a downward drag at the top of the list both scrolls the content AND pulls the sheet down simultaneously.
**Why it happens:** The browser doesn't distinguish between "drag the handle" intent and "scroll the list" intent from the pointer position alone.
**How to avoid:** Only attach the drag listener to the explicit handle element (`touch-action: none` on the handle div). Do NOT put the drag listener on the sheet container. The content area stays `overflow-y: auto` with `overscroll-behavior: contain`. At snap `peek`, where there is no scrollable content, the handle covers the whole visible strip so drag always works.

### Pitfall 3: Desktop CSS broken by new mobile-specific classes
**What goes wrong:** Adding `position: static` to `.entry-panel` in a new `@media (max-width: 768px)` block accidentally affects a rule that was used by both desktop and mobile.
**Why it happens:** The desktop panels use `position: fixed` without a media-query guard — it was the base style. Adding mobile overrides works, but any stray `!important` or specificity conflict can leak.
**How to avoid:** The new mobile rules should be scoped to a `.mobile-sheet-content` ancestor class that is only applied when `useIsMobile()` is true. Example: `@media (max-width: 768px) { .mobile-sheet-content .entry-panel { position: static; width: 100%; ... } }`. Never modify the base panel rules.

### Pitfall 4: MapLibre Popup z-index conflict with bottom sheet
**What goes wrong:** The existing `<Popup>` from `@vis.gl/react-maplibre` renders into a MapLibre-managed DOM subtree. Its z-index (managed by MapLibre) can appear beneath the bottom sheet scrim when the sheet is at full height, making the popup invisible.
**Why it happens:** MapLibre places popup DOM elements in the map canvas container, which is below the React-rendered sheet overlay.
**How to avoid:** At full-sheet height, the map is dimmed by the scrim and markers become non-interactive anyway (scrim has `pointer-events: auto`). No popup can be triggered at full-sheet height. At peek/half, the scrim is absent, the map is interactive, and MapLibre popups render at their normal z-index — no conflict. This is fine by design.

### Pitfall 5: iOS Safari 100vh / `dvh` unit
**What goes wrong:** `height: 100vh` on a fixed element includes the Safari toolbar area, causing the "full" snap height to extend behind the browser chrome.
**Why it happens:** iOS Safari's `100vh` = full screen including browser chrome, while the actual viewport is shorter.
**How to avoid:** Use `height: 100dvh` (dynamic viewport height, supported in iOS 16+ / Safari 15.4+) for the sheet's full-snap height. The project already targets phones — iOS 16 is a reasonable minimum baseline. Fallback: `height: calc(100vh - env(safe-area-inset-bottom))`.

### Pitfall 6: The `drp-popover` calendar is inside the panel
**What goes wrong:** The `DateRangePicker` renders its calendar as `position: absolute; z-index: 100` relative to the `.entry-panel`. Inside the bottom sheet at `peek` or `half` height, the calendar popover will be clipped by `overflow: hidden` on the sheet container.
**Why it happens:** The calendar's absolute positioning is relative to the entry panel, but the sheet container may have `overflow: hidden` to prevent content from escaping the rounded corners.
**How to avoid:** The sheet container must be `overflow: visible` (or `overflow: hidden` only on the content area, not the outer sheet wrapper). The outer sheet wrapper clips visually to the viewport — not with `overflow: hidden`, but with `border-radius` and `clip-path`. Alternatively, use a CSS `clip-path` on the bottom-rounded corners of the sheet and leave `overflow: visible` on the container. This is a known pattern for dropdowns inside draggable sheets.

## MapLibre fitBounds with Sheet Padding

### Current implementation (MapContainer.tsx, lines 62–65)
```typescript
map.getMap().fitBounds(
  [[Math.min(...lngs), Math.min(...lats)], [Math.max(...lngs), Math.max(...lats)]],
  { padding: 60, maxZoom: 9, duration: 600 },
);
```
This uses uniform `padding: 60` — no awareness of the sheet height.

### Required change
`FitRouteOnSelection` and any new finder fit function must accept a `bottomPadding` prop (the current sheet's snapped height in pixels) and pass it as:
```typescript
{ padding: { top: 60, bottom: bottomPadding + 60, left: 60, right: 60 }, maxZoom: 9, duration: 600 }
```
The `bottomPadding + 60` ensures visible markers appear above the sheet rather than hidden behind it.

### How to wire it
- Sheet component calls an `onSnapChange(snapIndex)` callback when the snap changes.
- `index.tsx` converts `snapIndex` to a pixel height (e.g. `SNAP_HEIGHTS = [80, window.innerHeight * 0.5, window.innerHeight]`) and passes it down to `MapContainer` as `sheetBottomPadding`.
- `FitRouteOnSelection` receives `sheetBottomPadding` from `MapContainer`'s props.
- Before `fitBounds`, call `map.getMap().setPadding({ top: 0, right: 0, bottom: 0, left: 0 })` to clear accumulated padding (see Pitfall 1).

### `FlyToCity` / `FlyToFinderRank1` (lines 76–105)
These use `flyTo` without padding — acceptable on mobile since they fly to a specific city for detail, not fitting a whole route. No change needed for these, but the note above about padding accumulation still applies: if `fitBounds` is called after a `flyTo`, reset padding first.

## Map Marker Mini-Popup on Mobile

### Current implementation
Both `StopMarkers.tsx` and `FinderMarkers.tsx` already implement `<Popup>` from `@vis.gl/react-maplibre` that shows on marker click. The popup is a small card with town name and score. This is the correct implementation for the "mini info-popup on the map" requirement.

### What needs to change
Per locked decisions: tapping a marker shows the popup **without forcing the sheet to change**. The current implementation already does this — `onStopClick` / `onFinderClick` in `index.tsx` currently triggers `setSelectedFinderIndex` which scrolls the sheet's list. This coupling must be broken on mobile:
- On mobile, a marker tap shows the popup (already works) but should NOT automatically snap the sheet to half/full or scroll the list.
- Option: Pass a `disableSheetScroll` flag or replace `onFinderClick` with separate `onMarkerClick` (map popup only) vs `onListItemClick` (sheet scroll + snap to half) callbacks.

### No new popup library needed
The existing `<Popup>` component from `@vis.gl/react-maplibre` is the correct tool. The popup already has `closeButton={false}` and the required town name + score content. Minor styling additions (mobile-larger tap target, improved typography) are CSS-only.

## Compact Search Bar — Reusing Existing Inputs

### Existing inputs
- `DateRangePicker` — self-contained, reads/writes `tripConfig.startDate/endDate` from Zustand store directly. No props to thread. Reusable as-is.
- `LocationInput` — reads/writes `searchAreas` from Zustand store directly. Reusable as-is.
- `CriteriaSelector` — reads/writes `tripConfig.criteria`. Reusable as-is.

### Collapsed state content
All values needed for the collapsed pill label come directly from the Zustand store:
- Location: `searchAreas[0]?.name` (e.g. "Bayern")
- Dates: `tripConfig.startDate` + `tripConfig.endDate` formatted as "3.–6. Jun"
- Criterion icon: `tripConfig.criteria[0]` → map to the existing icon component from `CriteriaSelector`

No new data fetching needed — the pill is a pure derived-display of existing store state.

### Expanded state
When the pill is tapped, the `MobileSearchBar` expands to show:
1. A mode toggle (route planning / weather finder) — currently spread across two CTA buttons in EntryPanel. On mobile, a two-segment control (`<button>` pair) replaces the verbose buttons.
2. `<DateRangePicker />` (unchanged component)
3. `<LocationInput />` (unchanged component)
4. `<CriteriaSelector />` (unchanged component)

The `DateRangePicker`'s calendar popover (`drp-popover`) uses `position: absolute` and `z-index: 100`. Inside the expanded search bar (which is `position: fixed` at the top), this should work correctly as long as the expanded bar does not have `overflow: hidden`. Verify: `z-index: 100` popover + `z-index: 50` search bar parent = the popover remains visible above other elements since it is a descendant of the search bar element. If the sheet (z-index 40) is visible beneath, the popover (z-index 100, within z-index 50 stacking context) appears above the sheet. Correct.

### Mode selection in search bar
EntryPanel's CTAs (`setMode('route-config')` / `setMode('weather-finder')`) become a mode toggle in the search bar's expanded form. The selected mode determines which additional config appears (RouteConfigStep vs WeatherFinderStep). These step components are already extracted and can be rendered below the shared inputs.

## Dark Mode — Design Token Usage

The project's `tokens.css` defines full `[data-theme="dark"]` overrides. New mobile components must use only token variables, not hardcoded values.

Key tokens for new UI:
- Sheet background: `var(--glass-bg)` + `var(--glass-border)` + `var(--glass-blur)` — same frosted glass as existing panels
- Search pill background: `var(--color-surface)` with `var(--shadow-glass)`
- Handle: `var(--color-border)` pill/capsule shape
- Scrim: `rgba(0,0,0,0.25)` at full height — this is a fixed value, acceptable since dark mode doesn't change scrim behavior
- Text: `var(--color-text)` / `var(--color-text-muted)` throughout

The `[data-theme]` attribute is applied on `<html>` by `themeStore.ts`. CSS variable inheritance means all child elements in the new sheet/search-bar components automatically inherit the correct theme tokens without any JS-side logic.

## Open Questions

1. **Landscape mode sheet height**
   - What we know: Locked decision says keep map-first; implementer decides.
   - What's unclear: At landscape on phone (e.g. 375×667 rotated → 667×375), `50vh` half-snap = 188px, which may be too short for the finder list.
   - Recommendation: Add a `@media (orientation: landscape) and (max-height: 500px)` rule that caps `peek` at 60px and `half` at 70% of viewport height. Defer full-landscape layout to a follow-up if it becomes a design concern.

2. **`onFinderClick` decoupling on mobile**
   - What we know: Currently clicking a map marker calls `onFinderClick` which also sets `selectedFinderIndex` and triggers `flyToCity`, and in `WeatherFinderPanel` the selected row scrolls into view.
   - What's unclear: Should a marker tap also snap the sheet to `half` (to partially reveal the list) or leave it unchanged?
   - Recommendation: On marker tap (mobile), show the popup only; do NOT change sheet snap. The user can then pull the sheet up manually. This matches Google Maps behavior.

3. **`DateRangePicker` calendar clipping inside sheet**
   - What we know: The popover is `position: absolute; top: calc(100% + 8px)` relative to the `.date-range-picker` container. Inside the sheet content area, if that area has `overflow: hidden`, the calendar is clipped.
   - What's unclear: The full-height sheet case — is `overflow: auto` on the content div sufficient, or does the picker need to be rendered via a portal?
   - Recommendation: Set `overflow: visible` on the sheet's outer wrapper and `overflow-y: auto` only on the inner content scroll area. Test on iOS Safari — if clipping persists, add a React portal render for the calendar popover in `DateRangePicker.tsx`.
